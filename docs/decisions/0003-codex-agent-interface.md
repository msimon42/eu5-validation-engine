# Codex is the CK3 product interface

Accepted 30 October 2026 through the user's requested replacement plan.

The user talks to Codex. A dedicated skill guides plain-language investigation,
small groups of concrete choices, and approved changes. A local MCP connector
uses the same deterministic engine and single job coordinator. The normal path
requires no browser, Node installation, dashboard, separate model service, or
OpenRouter key. Existing EU5 behavior and the optional developer dashboard remain
available; the preserved specification package is unchanged.

The user's preferences are CK3 first, Mac primary with Windows contracts retained,
separate fixes mods, small related choice groups, explicit separate tests for
uncertain changes, and enabling approved fixes only after checks. The first
release is not complete until a real feature conflict has been tested in CK3,
activated and undone. The initial investigation target is the shared call-allies
action in Unofficial Patch and More Interactive Vassals.

Server-owned proposals bind source identities, game/platform, exact proposed
bytes and alternatives. Model tool arguments cannot approve themselves. The
trusted local connector asks the user directly through MCP elicitation, then
signs that response for the engine. Decline/cancel creates no change. Approval
does not supply game evidence. Source updates, changed proposal content, wrong
workspace, or changed repair version refuse stale actions.

The MCP-facing process attaches to one loopback-only headless engine per managed
library instead of opening SQLite itself. The engine retains the original
source-copy, coordination and failure-recovery boundaries. Captured source
excerpts are bounded and honor configured exclusions; their contents are never
instructions to the agent. Complete result totals and searchable pages prevent
first-page summaries from pretending to describe the whole scan.

CK3's current preparation path can create an approved, inactive character-action
fix in managed state. This is not production activation. Unsupported game-data
isolation, unknown readers/composition, missing source payloads, absent runtime
observations or an unqualified activation adapter remain explicit obstacles.
No `approved=true`, clean parser, synthetic replay, or user preference can bypass
the evidence/preservation requirements. The implementation status must distinguish
working agent tools from the still-required actual game acceptance milestone.
